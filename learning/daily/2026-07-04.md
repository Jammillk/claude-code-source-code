## 核心理解

### 1. API 对接的三个层次

| 层次 | 代码 | 职责 |
|------|------|------|
| 读取密钥 | `load_config()` → `config.json` | 从配置文件拿到 `api_key` |
| 建连接 | `OpenAI(api_key=..., base_url=...)` | 创建 HTTP 客户端 |
| 发请求 | `client.chat.completions.create(...)` | 把 messages[] + tools 发过去 |

### 2. API 返回结构

```python
response = {
    "choices": [{              # 数组，默认长度=1（n=1）
        "message": {           # 模型回答
            "role": "assistant",
            "content": "...",      # 文字（可能 null）
            "tool_calls": [...]    # 工具调用（可能 null）
        },
        "finish_reason": "stop"  # 为什么停了
    }],
}
```

`choices[0]` 是因为 API 支持 `n=3` 一次出多个答案，默认 `n=1`。

### 3. `finish_reason` 的机制

**API 服务器返回的，不是 prompt 里写的。** 模型训练时植入了特殊 token（如 `<|endoftext|>`），服务器检测后自动设置：

| 值 | 触发 | 处理 |
|----|------|------|
| `"stop"` | 输出结束 token | 退出循环 |
| `"tool_calls"` | 输出工具调用格式 | 执行工具 → 继续循环 |
| `"length"` | 达到 max_tokens 上限 | 可继续追问 |
| `"content_filter"` | 安全审核触发 | 报错退出 |

### 4. messages[] 会越积越多 — Agent 的核心难题

每次 API 调用都带上完整历史，工具调用轮次越多 messages 越长。Claude Code 的解决方案：`src/services/compact/`（自动摘要、裁剪、折叠）。

### 5. 工具定义的跨厂商适配

- OpenAI/DeepSeek：`{"type":"function","function":{...}}`
- Anthropic/Claude：`{"name":"...","input_schema":{...}}`
- 国内模型多数兼容 OpenAI 格式
- 工具**内容**完全由开发者定义，格式跟随厂商

### 6. 每次"想-做"循环 = 一次 API 调用（计费）

```
第 1 次 API：模型决定要调工具 → finish_reason="tool_calls"
    ↓ 本地执行（毫秒级，不计费）
第 2 次 API：模型拿到工具结果 → 继续思考或回答
    ↓
...每轮都计费，messages 越来越长
```

为什么感知不到？
- 工具在本地执行，毫秒级
- DeepSeek 速度快
- 流式输出掩盖等待时间

慢工具（网络请求、大文件读取）会卡住 Agent，这就是需要并行执行的原因。

### 7. 模型行为不可精确控制

工具参数缺失时（如 send_email 的 to 未知），模型可能追问也可能瞎猜。Claude Code 通过千行 system prompt + permission hooks 来引导模型行为。

## Topic 02: 工具系统 — buildTool() 工厂模式

### 源码对照

`src/Tool.ts` 第 757-792 行的核心设计:

```typescript
// 1. 安全默认值（fail-closed）
const TOOL_DEFAULTS = {
  isEnabled: () => true,
  isConcurrencySafe: () => false,   // ← 默认不能并行
  isReadOnly: () => false,          // ← 默认有副作用
  isDestructive: () => false,
  checkPermissions: () => ({ behavior: 'allow' }),
}

// 2. buildTool() 工厂 — 第 783 行
export function buildTool(def) {
  return { ...TOOL_DEFAULTS, userFacingName: () => def.name, ...def }
}
```

一个工具定义只需要传 `name + description + handler`，buildTool 帮你补上 7 个默认方法。

### 之前 vs 现在

| | Topic 01 (if/elif) | Topic 02 (ToolRegistry) |
|---|---|---|
| 加一个工具 | 改 TOOLS 列表 + 改 execute_tool | registry.register(Tool(...)) |
| 校验输入 | 手动 if not field | tool.validate() 自动 |
| 跨厂商格式 | 手动改 JSON | tool.to_openai_schema() / to_anthropic_schema() |
| 能力标记 | 无 | is_read_only / is_destructive / is_concurrency_safe |

### 实践文件

- `learning/topics/02-tool-system/tool_system.py` — Tool 类 + build_tool + ToolRegistry
- `learning/topics/02-tool-system/agent_v2.py` — 用新工具系统重写的 Agent 循环

核心改进：`registry.dispatch(name, args)` 替代了 `if/elif` 硬编码。

### 关键学习点

1. **工厂模式的价值**: 统一默认值，新工具只需要关心自己的逻辑
2. **fail-closed**: isConcurrencySafe 默认 false，防止意外并行
3. **注册表 = dispatch map**: 64 个工具也只是一个字典
4. **schema 生成独立**: 工具定义和 API 格式解耦，切换厂商不需要改工具逻辑
